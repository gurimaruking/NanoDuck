# NanoDuck — MicroDuck を MG90S でサイズダウンする

MicroDuck (250 mm / 737 g / Dynamixel XL330 ×14) を、ホビーサーボ **MG90S** で
成立するサイズまで縮小するための設計検討。

数値はすべて、**実機出荷版の歩行ポリシー `alpha_walking.onnx` を CPU MuJoCo で
30 秒走らせて実測した関節トルク・角速度**（`analysis/microduck_demand.npz`,
5348 サンプル × 14 関節）から導いている。カタログ値の掛け算ではない。

```
analysis/  サイズ決定の計算       servo_sizing.py
sim/       MG90S アクチュエータモデル  run_mg90s.py --servo mg90s-6v --view
cad/       メッシュとスケール       check_servo_fit.py  ← 部品を買う前にこれ
bom/       部品表と電装の判断       bom.csv
```

## 0. いま分かっていること(3行)

1. **トルクは s ≤ 0.56(140 mm)なら足りる** — 律速は膝の「出力(W)」で、減速比では救えない
2. **しかし幾何が入らない** — MG90S は XL330 の 95 % の長さしかなく、
   同じ実装密度なら s ≥ 0.95 が要る。**制約が交差していて窓が無い**
3. **抜け道は DOF 削減とサーボ混載** — v1 BOM は 14 → 12 DOF、脚 MG90S ×10 +
   首頭マイクロサーボ ×2 で組んでいる。股関節はまだ密で、機構設計が最大の未解決項目

## 1. 結論

| | 高さ | 質量 | 構成 |
|---|---|---|---|
| MicroDuck | 250 mm | 737 g | XL330 ×14 @ 7.4 V (2S LiPo) |
| **NanoDuck v1** | **140 mm** (s=0.56) | **287 g** | MG90S ×10 + マイクロ ×2 @ **6.0 V**、12 DOF |
| MG90S @ 4.8 V なら | 100 mm (s=0.40) | 約 285 g | 6 V 化を強く推奨 |

287 g は [bom/bom.csv](bom/bom.csv) の実部品積み上げ。
モデルの予算 320 g を下回るのは 14 → 12 DOF の分で、**浮いた 33 g はそのまま
膝のトルク余裕に返ってくる**（トルク ∝ 質量 × モーメントアーム）。

### 質量には床(floor)がある

サーボ・電池・基板は**縮まない**。s³ で縮むのは構造材だけ:

| s | 高さ | 質量 | 内訳 |
|---|---|---|---|
| 0.8 | 200 mm | 439 g | 固定 263 + 構造 177 |
| 0.6 | 150 mm | 337 g | 固定 263 + 構造 75 |
| **0.5** | 125 mm | 306 g | 固定 263 + 構造 43 |
| 0.4 | 100 mm | 285 g | 固定 263 + 構造 22 |
| 0.3 | 75 mm | 272 g | 固定 263 + 構造 9 |

MicroDuck では固定質量が全体の 53 % だが、NanoDuck では **86 %** — 「サーボの袋」になる。
**s=0.5 より小さくしても質量はほとんど減らない**(306→285 g)。ここが縮小の収穫逓減点。

> 初期の見積りではバッテリと電子部品を s³ 項に入れていた。500 mAh の LiPo は
> 縮まないので、これは小スケールを不当に有利に見せる誤りだった。
> CAD メッシュの実測（`np_f970.stl` は名前に反し **NP-F550 寸法と 0.2 mm 一致** = 約 76 g）
> で 3 項モデル（サーボ 252 g / 電装 140 g / 構造 345 g）に組み直してある。

### ただし「小さくできる」は「作れる」ではない

トルクは s ≤ 0.56 で足りるが、**MG90S が幾何的に入らない**。
これが最大の未解決項目 → [cad/README.md](cad/README.md)

## 2. なぜそんなに小さくなるのか — 律速は膝の「出力(W)」

関節需要の実測 (p99):

| 関節 | トルク | 角速度 |
|---|---|---|
| **left_knee** | **0.488 Nm** | **6.64 rad/s (380°/s)** |
| right_knee | 0.444 Nm | 5.66 rad/s |
| right_hip_pitch | 0.301 Nm | 4.47 rad/s |
| left_ankle | 0.214 Nm | 3.56 rad/s |
| （他 10 関節） | ≤ 0.19 Nm | ≤ 3.2 rad/s |

膝が 2 番目の関節の **2.3 倍**。しかも膝はトルクと速度の**両方**で最悪。

機械出力で見ると差が決定的:

```
MicroDuck 膝の必要出力 (p99)      2.85 W
XL330 @7.4V の最大機械出力        4.87 W   ← 余裕は 1.7 倍しかない
XL330 @6.5V (電池終盤)            3.76 W
MG90S @6.0V                       0.71 W   ← XL330 の 15 %
MG90S @4.8V                       0.46 W
```

サーボのトルク-速度包絡線は `τ_max(ω) = min(τ_cap, τ_stall·(1−ω/ω_noload))`。
XL330 は BAM 実測フィット (kt=0.3660 Nm/A, R=2.8114 Ω) と実際の駆動電圧
（`vin_range` = 6.5–8.2 V の 2S LiPo。データシートの 5 V ではない）から
τ_stall = kt·V/R = **0.963 Nm** — MJCF の `forcerange ±0.96` と完全一致するので、
これが出荷ポリシーの学習対象そのものだと確認できる。ファーム電流制限
1.75 A が kt·1.75 = 0.641 Nm で頭打ちにするため、包絡線は「平坦→線形降下」。

**ここが肝**: 出力が足りないとき、減速比では救えない。
ギヤはトルクと速度を交換するだけで積 (=出力) を変えないからだ。
実際、膝に 2:1 を入れると必要サーボ速度が 6.6 → 13.3 rad/s となり、
MG90S の**無負荷速度 13.1 rad/s を超える** — トルクは得たが回せない。

そして小型化は速度要求を**悪化させる**。脚は倒立振子なので歩行周期 ∝ √(L/g)、
つまり小さいほど速く振る必要がある (ω ∝ 1/√s)。
トルクは s⁴ 的に楽になるが、速度は 1/√s で厳しくなる — この綱引きの解が s ≈ 0.5–0.55。

出力の要求は s とともにこう下がる（Froude 相似歩容）:

| s | 高さ | 質量 | 膝の必要出力 |
|---|---|---|---|
| 0.7 | 175 mm | 354 g | 1.14 W |
| 0.6 | 150 mm | 292 g | 0.88 W |
| **0.5** | **125 mm** | **248 g** | **0.68 W** ← MG90S@6V の 0.71 W にちょうど収まる |
| 0.4 | 100 mm | 219 g | 0.53 W |

### スケーリング則（本解析の仮定）

```
長さ            L      → s·L
サーボ以外の質量 m_ns   → s³·m_ns      （シェル・ブラケットは体積で縮む）
サーボ質量       m_srv  → 固定          ★ 買ってきた部品は縮まない
関節トルク       τ      → τ·(M(s)/M0)·s   (τ ~ M·g·L)
関節速度         ω      → ω/√s (Froude) または ω (同一周期)
```

★ が効く。s=0.55 では構造材は 0.17 倍になるのに、サーボ 14 個 (188 g) は
そのまま残る → 総質量 265 g のうち **71 % がサーボ**。
「小さくすれば軽くなる」が途中で頭打ちになる。

### 妥当性チェック

同じ計算を XL330 @7.4 V に当てると **s ≤ 1.09 まで成立、実機サイズ s=1.0 では膝が約 90 %**
と出る。「限界設計だが成立している」という実機の実態を再現しており、
解析のキャリブレーションが取れている。s=1.0 が 30 % 余っていたり逆に破綻していたら、
この解析は信用できない。

なお `s ≤ 1.09` は「XL330 のままなら 272 mm まで大きくできる」という意味でもある。

## 3. トルク以前の問題 — MG90S には位置フィードバックが無い

これがサイズより重い課題。

ポリシーの観測は **61 次元**:

```
base_ang_vel(3) + gravity(3) + joint_pos(14) + joint_vel(14) + last_action(14) = 48
                                                            + command(13)      = 61
```

**48 次元中 28 次元 (58 %) が関節エンコーダ由来**。MG90S は PWM 位置指令のみで
出力を返さないので、そのままでは観測が作れない。
（学習側も `ENABLE_ENCODER_BIAS = True` でエンコーダ較正誤差をランダム化しており、
フィードバック前提の設計になっている。）

取りうる選択肢:

| 案 | 内容 | 代償 |
|---|---|---|
| **A. ポテンショ・タップ** | MG90S 内部の 5 kΩ ポテンショのワイパーを引き出し、ADC 16ch (ADS1115 ×4 等) で読む | 14 個ハンダ改造 + 個体較正。**観測契約とポリシー構成をそのまま使える** |
| **B. フィードバック無しで再学習** | 観測を IMU + last_action のみ (20 次元) に変更して全ポリシー再学習 | ハード改造ゼロ。ただし観測契約が変わり sim2real 難度が上がる。全 9 ポリシー作り直し |
| **C. フィードバック付き小型サーボに変更** | Feetech SCS0009 / STS3032 等（バス接続・位置フィードバック有） | 「MG90S で」から外れる。ただし XL330 の 1/5〜1/10 価格で契約は維持 |

推奨は **A**（MG90S 縛りを守るなら）または **C**（コスト目的が主なら）。

### その他の実装差分

- **バス配線**: XL330 は TTL デイジーチェーン 1 本。MG90S は 14 本の PWM 線が要る
  → PCA9685 (16ch, I2C) か MCU 経由。制御ループ 50 Hz に対し PWM 標準 50 Hz は
  最大 20 ms の遅延を足す（`--delay` と command-delay DR で吸収可能な範囲か要検証）
- **電源**: MG90S ストール電流 ~700 mA ×14 = 最悪 10 A @6 V。5 A 級 BEC は必須
- **バックラッシ**: 現行モデルは ±1°。MG90S(金属ギヤ)は実測で ±1〜2° 程度を想定し
  `add_backlash.py` の値を広げる
- **寸法**: ⚠️ **ここが本丸**。MG90S は XL330 の 95 % の長さがあり、実質縮んでいない。
  「体積は 45 % 小さい」は事実だがミスリード（連鎖方向の長さが制約なので）。
  詳細と抜け道は [cad/README.md](cad/README.md)。
  なお出力軸が片側のみなので、反対側に軸受け／アイドラを自作する必要もある

## 4. MG90S アクチュエータモデル — 実装済み & 検証済み

`sim/mg90s.py` に MG90S のアクチュエータモデルを実装した。
`sim/run_mg90s.py` が microduck_rl の `infer_policy.py` をそのまま駆動し、
**アクチュエータだけ**を差し替えるので、結果の差はサーボ以外の何物でもない。

```bash
cd NanoDuck/sim
python run_mg90s.py --servo xl330      # 対照群
python run_mg90s.py --servo mg90s-6v   # 本命
python run_mg90s.py --servo mg90s-6v --view   # ビューアで見る
```

モデルは MuJoCo の `position` アクチュエータを**トルクモードに変換**して
毎物理ステップで自前計算する:

```
err  = deadband(q_target − q)          # ポテンショは出力軸を読む
u    = clip(kp·err / τ_stall, −1, +1)  # アナログP制御 → PWMデューティ
τ    = τ_stall·u − (τ_stall/ω_noload)·q̇
```

第2項が逆起電力で、これが**トルク-速度の三角形**を作る。`position` アクチュエータの
平坦な `forcerange` では「速く回すほどトルクが出ない」を表現できず、
ベンチでは崩れるロボットがシム内では平然と歩いてしまう。

### 対照群による較正（これが無いと信用できない）

最初の実装は「誤差1°でフルドライブ」= 実効剛性 55 Nm/rad とし、MJCF の
`chosen_actuator` が定める **kp = 0.55 Nm/rad の100倍**だった。結果、
**XL330 の数値でも 2.4 秒で転倒**。対照群が歩かないならモデルが悪い。
剛性をサーボ内部ゲインではなく**関節剛性 kp [Nm/rad]** で直接パラメータ化して修正。

副産物として良い整合が取れた: MJCF の `damping=0.053` は逆起電力項を持たない
position モデル用にフィットされた値なので逆起電力を吸収しているはず。
実際 0.053 − (0.963/20.2) = **0.0054** で、BAM が独立にフィットした
`friction_viscous = 0.00536` と **1 % 以内で一致**する。この分解は物理的に正しい。

### 結果（MicroDuck 実寸 s=1.0、出荷版歩行ポリシー、15 s）

| サーボ | 結果 |
|---|---|
| XL330 @7.4V（対照群） | **歩く** 2.65 m / 14.3 s、飽和 0 % |
| MG90S @6.0V | **1.1 s で転倒**、飽和 64 % |
| MG90S @4.8V | **1.0 s で転倒**、飽和 58 % |

### どちらが効いているのか — アブレーション

MG90S は XL330 と2つの独立な点で違う: **出力(W)** と **制御則**。
片方ずつ入れ替えて切り分けた結果、**実寸ではどちらも単独で致命的**だった:

| 条件 | 結果 |
|---|---|
| MG90S の出力 + XL330 の制御則 | 1.7 s で転倒 ← 出力不足だけで死ぬ |
| XL330 の出力 + MG90S の制御則 | 1.9 s で転倒 ← 制御則だけでも死ぬ |

さらに制御則の3要素を分離すると、犯人は**剛性ひとつ**だった:

| 変更（XL330 の出力のまま） | 結果 |
|---|---|
| 不感帯 1.0° | **歩く**（飽和 0 %） |
| 指令遅延 20 ms（50 Hz PWM 1フレーム分） | **歩く** |
| kp 0.8 / 1.0 / 1.2 Nm/rad | **歩く** |
| kp 1.5 Nm/rad | 5.1 s で転倒 |
| **kp 2.47 Nm/rad**（MG90S 相当） | **0.8 s で転倒** |

**ハード設計への含意:**

- **333 Hz PWM は不要**。標準 50 Hz の 20 ms 遅延は問題にならない
- **不感帯 1° も許容範囲**。姿勢精度は落ちるが安定性は壊さない
  （ただしこれはフィードバック **有り** 前提。§3 の A 案が要る）
- **効くのは関節剛性ひとつ**。MG90S は自身のトルクに対して XL330 の
  約 4.5 倍硬く、出荷ポリシーの許容上限（kp ≈ 1.2–1.5）を超える

ただしこれは**未再学習のポリシー**の話。RL は硬いアクチュエータを扱えるので、
kp ≈ 2.5 をドメインランダム化に含めて学習し直せば解ける見込みが高い。
つまり結論は「MG90S は無理」ではなく **「再学習は必須で、そのとき剛性を
正しく入れることが最重要パラメータ」**。

## 5. 作業手順（sim ファースト）

CAD を先に引くと、歩けないロボットを 3D プリントすることになる。順序が重要。

1. ~~**MG90S アクチュエータモデルを作る**~~ → §4 で完了。
   ただし `kp` / `deadband_rad` / `frictionloss` はカタログ値ではなく**推定値**。
   MG90S は互換品で個体差が激しいので、リポジトリのテストベンチ
   (`scripts/validate_bam_testbench.py`, `robot/xl330_test_bench/`) で
   実測してから sim2real を信用すること。特に **kp は最重要**（§4）
2. **スケール MJCF を生成**
   `robot_walk.xml` を s 倍（長さ s、質量 s³、慣性 s⁵）してサーボ質量だけ差し替え。
   Onshape CAD は公開されている:
   https://cad.onshape.com/documents/804927696f06d877f3f1803e
   → 自分のドキュメントにコピーして寸法を変更し、`onshape-to-robot` で再エクスポート
   （`config_mjcf_walk.json` がそのまま設定ファイルになる）
3. **観測契約を決める**（§3 の A / B / C）— ここで全部が分岐する
4. **歩行を再学習** `Mjlab-Velocity-Flat-NanoDuck` を登録して PPO
5. **`infer_policy.py` で確認** → 実機へ
